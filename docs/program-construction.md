# 使用起末范式构建程序

## 核心原则

使用起末范式构建程序时，最终结构必须在最开始就被确定。

这不是传统意义上的“先写需求，再开发实现”，而是：

```text
末端结构先定
达末路径围绕末端生成
中间结构不能偏离末端
偏离则闭环失败
```

因此，一个程序不是先从入口函数开始写，也不是先堆功能模块，而是先定义它最终必须闭合成什么状态。

## 与传统程序构建的区别

传统程序构建常见路径是：

```text
需求 -> 设计 -> 编码 -> 测试 -> 修 bug -> 上线 -> 再补丁
```

这个过程可能不断跑偏。因为最终结构常常不是一开始就被严格闭合，而是在开发过程中被不断解释、修改、兼容和修补。

起末范式的构建路径是：

```text
起 -> 末端定局 -> 完整语义 -> 状态结构 -> 达末路径 -> 闭环验证
```

如果最终结构不是最开始定下的末端，整个结构就无法闭环。

## 终局先定

在起末范式中，程序的最终结果不是开发完成后才出现的未知数。

最终结构必须在构建之初被定为“末”。

例如，要构建一个“得到苹果”的程序，不能只写：

```text
搜索苹果
返回购买链接
```

而要先定义末端：

```text
我真实拥有一个苹果
并且获得方式合法、安全、可验证
```

之后所有中间结构都只能围绕这个末端展开。

## 不可跑偏

起末范式中的“不可跑偏”不是说过程不会遇到错误，而是说错误不能被系统当成正常结果吞掉。

如果中间路径偏离末端，系统必须识别出闭环失败：

```text
预定末端：我拥有一个苹果
实际结果：我只获得了一个购买链接
判断：末端未成立，闭环失败
```

因此，起末范式不允许把“流程跑完”伪装成“末端达成”。

## 小结构内嵌规则和质检

使用起末范式构建程序时，规则和质检不是最后外挂上去的测试层。

每个小结构在构建时就必须包含：

```text
规则
质检
失败判定
回流机制
```

也就是说，小结构本身就要能回答：

```text
我是否接收到了正确前置条件？
我是否生成了正确中间产物？
我的产物是否能被下一个结构读取？
如果不能，我是否必须回流修正？
```

如果一个小结构需要靠外部补丁才能保持正确，它就还没有完成闭环。

## 闭环失败条件

以下情况都属于闭环失败：

- 最终状态不是最开始定义的末端
- 只返回了中间结果
- 路径表面达末但破坏约束
- 错误被跳过后继续伪装成功
- 输出正确文本但真实状态没有变化
- 程序执行结束但目标没有成立
- 任意小结构没有通过自身质检
- 任意小结构的输出不能被下一结构读取
- 任意小结构失败后被补丁绕过

## 构建一个程序的最小步骤

使用起末范式构建程序，至少需要先回答：

```text
1. 起是什么？
2. 末是什么？
3. 末端成立的验证条件是什么？
4. 哪些路径可以达末？
5. 哪些路径必须被排除？
6. 中间状态如何记录？
7. 如果未达末，如何继续演化？
```

只有这些结构确定后，才进入实现。

## 核心定义

起末范式下的程序不是一组从入口开始执行的指令。

它是一个从起发生、以末定局、由完整语义和达末机制推动，并以闭环验证作为完成条件的结构。
