# 起末范式基础公理

## 0. 问题背景

数字世界本身具有纯粹性。

```text
1 就是 1
1.2 就是 1.2
```

但在现有计算机体系中，人类思维、业务语义、历史兼容、抽象层、框架和人为约定不断叠加到数字结构之上，导致底层符号经常不再保持它最初的确定性。

例如，同一个 `1` 在不同系统里可能代表：

- 数值一
- 布尔真
- 状态启用
- 权限允许
- 用户等级
- 错误码
- 枚举值
- 某种业务含义

这不是数字世界自身的问题，而是人类语义被强行灌入底层结构之后产生的混淆。

起末范式从底层开始阻断这种混淆。

## 1. 数字恒等公理

在起末范式中，数字首先只保持自身。

```text
1 = 1
1.2 = 1.2
```

数字不能在底层被随意赋予人类语义。

如果一个系统要表达“启用”“完成”“允许”“错误”“等级”等含义，它不能直接污染数字本体，而必须在起末范式的结构层中显式声明。

也就是说：

```text
错误方式：1 自动代表 true、enabled、done 或 allowed
正确方式：语义结构声明某个状态成立
```

## 2. 符号纯粹公理

符号在底层也必须先保持自身。

一个符号不是因为人类习惯、业务场景或历史框架而自动拥有意义。

意义必须经过起末范式的结构化过程进入系统：

```text
起 -> 语义结构 -> 状态场 -> 达末机制 -> 末
```

这意味着人类语义不能直接穿透到底层符号。

## 3. 人类语义阻断公理

起末范式不是不要人类意图，而是阻断人类思维对底层的直接污染。

人的目标、欲望、问题和缺口可以成为“起”，但不能直接改写底层规则。

它们必须被转换为起末范式内部可验证、可演化、可闭环的结构：

```text
人的表达：我想要一个苹果
范式结构：
  起：我想要一个苹果
  末：我最终拥有一个苹果
  状态：当前是否拥有苹果
  约束：苹果必须真实存在并可取得
  达末：生成并执行可行路径
```

这样，人类意图被接收，但不会让底层数字和符号失去恒等性。

## 4. 规则内生公理

起末范式中的规则不从传统计算机体系、历史框架或人类习惯中默认继承。

所有规则必须从起末结构中生成或声明：

- 起是什么
- 末是什么
- 当前状态是什么
- 状态如何演化
- 哪些约束必须保持
- 如何判断末端成立
- 如果末端未成立，如何继续演化

规则不是外部补丁，而是闭环结构的一部分。

## 4.1 非静默公理

起末范式不允许底层结构静默处理错误。

无法解析、无法匹配、无法验证或无法闭环的状态，必须显式进入结构。

```text
无法解析 -> 未闭环
无法匹配 -> 结构缺口
无法验证 -> 质检失败
无法达末 -> 回流任务
```

系统不能为了让流程继续运行，就把错误悄悄吞掉、默认化或包装成成功。

静默处理不是可靠性，而是隐藏未闭环状态。

## 5. 闭环必达公理

起末范式的最终结构不是开放流程，而是闭环结构。

传统体系常见结构是：

```text
输入 -> 程序 -> 输出
```

这个结构的结果可能正确，也可能错误；可能达成目标，也可能只是流程跑完。

起末范式要求结构闭合：

```text
起 -> 达末机制 -> 末 -> 验证 -> 未达则再演化 -> 末成立
```

因此，系统的重点不是“执行过”，而是“闭环是否成立”。

## 6. 起末范式的底层边界

起末范式的底层边界可以概括为：

```text
数字保持数字
符号保持符号
人类语义不得直接污染底层
未闭环状态不得静默处理
所有意义必须进入起末结构
所有规则必须服务于末端闭环
```

这使起末范式不是在旧计算机体系上增加一层解释器，而是从底层规则开始重新构建计算秩序。
