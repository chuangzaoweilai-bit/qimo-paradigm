# 对传统计算机体系的批判

## 问题

当前主流计算机体系建立在一个隐含前提上：

```text
计算从一个正确的开始点出发。
```

这个开始点通常是程序入口、函数调用、命令执行、系统启动、请求到达或某个预设事件。

但真实世界里的目标并不总是这样发生。

人不是先拥有一个严格定义好的程序入口，然后再表达目标。人往往是先有一个缺口、欲望、问题或未完成状态：

```text
我想要一个苹果。
我不想处在现在这个状态。
某件事必须被完成。
某个结果必须出现。
```

传统体系会把这些起点压缩成输入，然后交给已经写好的程序处理。程序跑完以后，系统通常只关心是否执行结束，而不保证最终状态是否就是人真正要的末端。

## 结构性缺陷

传统体系常见的执行结构可以概括为：

```text
开始 -> 执行 -> 异常 -> 跳过或补救 -> 继续执行 -> 返回未知结果
```

这种结构的问题不是某个程序写得不好，而是体系本身更重视“流程能否跑完”，而不是“末端是否必然达成”。

当错误出现时，系统常见处理方式是：

- 跳过错误
- 捕获异常
- 增加条件分支
- 加一层适配器
- 再写一个补丁
- 把失败包装成另一个返回值

这些方法在工程上有价值，但它们没有改变底层结构：系统仍然不是围绕必达末端组织计算。

## 补丁被误认为创新

当旧体系不能抵达目标时，常见路径是继续增加新层：

```text
库
框架
中间件
平台
虚拟机
容器
编排系统
自动化脚本
AI agent
```

这些层可以提高效率，也可以解决局部问题，但如果它们仍然建立在“输入、程序、输出”的旧结构上，它们就只是在原体系上继续缝补。

缝补可以让系统更复杂、更能跑、更像智能，但不等于改变了计算的第一性基础。

## 最终结果仍是未知数

在传统体系里，一个系统可以：

- 正常启动
- 正常执行
- 正常返回
- 正常记录日志
- 正常通过测试

但它仍然可能没有抵达真正想要的末端。

例如：

```text
起：我想要一个苹果
传统结果：返回苹果购买链接
真实末端：我最终拥有一个苹果
```

返回链接不是末端成立。程序执行结束也不是末端成立。只有“我最终真实拥有一个苹果”才是末端成立。

## 起末范式的反转

起末范式不把“开始执行”视为唯一正确起点。

它把起点扩展为任何真实发生的目标、缺口、欲望、状态差异或问题。

它也不把“程序跑完”视为计算完成。

它把末端定义为必须成立的终局状态。

因此，起末范式的核心反转是：

```text
旧体系：从开始出发，接受未知结果。
起末范式：从起发生，以末必达为组织原则。
```

## 关键区别

| 维度 | 传统体系 | 起末范式 |
| --- | --- | --- |
| 起点 | 程序入口或预设输入 | 目标、缺口、欲望、状态差异 |
| 中间 | 执行固定流程 | 生成、选择、修正达末路径 |
| 错误 | 捕获、跳过、补丁 | 作为达末路径失败信号 |
| 创新 | 增加新层或工具 | 改变计算组织原则 |
| 完成 | 程序结束或返回结果 | 末端状态真实成立 |
