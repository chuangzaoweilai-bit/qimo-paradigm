# 起末范式

[English README](README.en.md) | [English Whitepaper](docs/whitepaper.en.md)

起末范式是一套重新定义计算机体系的实验性计算范式。

它不以传统计算机中的程序、文件、进程、内存、指令集、操作系统或应用软件作为第一性基础，而是尝试从更高层的语义、状态、关系与演化过程重新组织计算。

起末范式是一套全领域底层范式。它不是区块链专用，也不是 AI 专用；区块链语义训练闭环只是早期实验样例，用来说明它如何在复杂领域中落地。

这个项目选择免费公开。公开目的不是封闭占有，而是让这套新的计算机底层范式真正进入大众视野，并希望它被善用。

希望大家能不断完善和维护它。一套全新的计算机体系诞生，需要所有人共同的努力。

一个最简单的例子：

```text
起：我想要一个苹果
末：我最终一定会得到一个苹果
中间：系统如何让这个末端必然达成
```

在这个例子中，起不是普通输入，末也不是普通输出。起是欲望、目标或问题的发生，末是必须被达成的终局状态，中间过程则是系统围绕末端生成路径、执行动作、处理阻碍、验证结果并持续推进的计算过程。

## 核心定位

起末范式关注的问题不是“如何在现有计算机上写出另一种程序”，而是：

- 如果不默认传统计算机结构是唯一基础，计算应当从什么开始？
- 一个计算系统的最小存在单位是什么？
- 状态、语义、执行、反馈和外部世界之间应当如何连接？
- 人、机器、任务、知识与环境能否被纳入同一套计算结构？
- 不同领域能否被同一套起、末、路径、规则、质检和闭环结构重新组织？

## 对旧体系的核心批判

当前主流计算机体系通常默认一个固定起点：程序开始执行。

但现实中的计算并不总是从这个唯一正确的起点发生。人的目标、环境变化、状态缺口、失败反馈和未完成结果，常常都被迫压缩成程序输入、异常处理、补丁逻辑或外围工具。

于是旧体系容易形成一种结构性问题：

```text
唯一开始 -> 跳过错误 -> 跑遍流程 -> 补丁修补 -> 结果未知
```

很多所谓创新，本质上是在旧基础上不断缝补。系统可以跑完，却不保证抵达真正想要的末端。

起末范式要改变的正是这一点：计算不应只保证“流程被执行”，而应围绕“末端必然成立”组织自身。

起末范式也反对底层静默处理。无法解析、无法匹配、无法验证或无法闭环的状态，不应被系统悄悄吞掉、跳过或包装成成功，而必须显式进入结构并触发回流。

## 基础公理

起末范式从底层阻断人类思维对数字世界的直接污染。

在数字世界中：

```text
1 就是 1
1.2 就是 1.2
```

如果 `1` 在不同系统中被强行解释为真、启用、完成、允许、等级或错误码，那不是数字本身发生了变化，而是人类语义污染了底层符号。

起末范式要求数字和符号先保持自身，人的目标只能作为“起”进入系统，经过起末结构变成可验证、可演化、可闭环的状态，而不能直接改写底层规则。

## 完整语义

起末范式认为，当前 AI 的语义大多是碎片化的。

以“我想要一个苹果”为例，AI 不能只给出“去买一个”这样的单一路径。完整语义应当记录一个事物在多个场景下的路径，包括正确方法、错误方法、不可行方法、危险方法和禁止方法。

例如，“自己买一个”“让别人帮忙买”“线上下单”“家里已有直接取得”都是可行或条件路径；“抢一个苹果”也必须被语义库记录，但它应被标记为违法、危险或禁止路径，不能作为执行建议。

完整不是只记录正确答案，而是记录足够完整的场景、路径、约束和排除项，让系统知道如何合法、安全、真实地达末。

## 达末路径扩展

“一定会得到”不是只依赖当前手里已有的资源。

如果“我想要一个苹果”，而我自己没有钱或附近没有可直接购买路径，系统不能立刻判定失败。它必须继续扩展允许路径：

```text
父母买一个苹果给我
朋友买一个苹果给我
店主自愿赠予一个
经允许在果园采摘一个
通过交换、配送、请求协助等方式获得
```

因此，资源不足不是终点，而是路径扩展信号。只要末端未成立，系统就必须继续从完整语义中寻找合法、安全、可验证的达末路径。

## 大众化计算

起末范式不把昂贵设备和大模型作为普通人参与智能计算的必需前提。

当前 AI 体系大量依赖大规模语料、高额算力和中心化大模型。起末范式更关注如何通过闭环语义结构，让普通人也能构建自己的专业语义系统。

它追求的不是更大的模型，而是更完整的语义、更明确的末端、更可验证的闭环。

## 多容器语义训练闭环

早期实验曾使用三容器组合来构建区块链语义闭环：

```text
起：我要获得完整的区块链语义
末：我一定会获得完整的区块链语义

容器 1：拉取链上智能合约，生成区块链阶段性任务清单
容器 2：只有读取到任务清单，才阶段性训练生成语料
容器 3：只有读取到语料，才训练推理生成完整语义条目
```

这个结构不是普通流水线，而是一个闭环：

```text
链上智能合约 -> 阶段任务 -> 阶段语料 -> 语义条目 -> 容器 1 反向核对任务执行 -> 缺口补齐 -> 新阶段任务
```

它说明起末范式可以不依赖现成的完整语义库，而是从领域目标出发逐步生成专业语义。

## 构建程序

如果使用起末范式构建程序，最终结构在开始构建时就必须成为定局。

传统程序可以从入口开始写，再不断测试、修补、兼容和解释结果。起末范式不这样构建。它先定义末端结构，再让所有语义、状态、路径和规则围绕这个末端闭合。

如果最终结构不是最开始定义的末端，那么整个结构就无法闭环。

因此，起末范式下的程序不会把“跑完流程”当成成功。它只承认“末端真实成立”。

## 结构闭环

起末范式中的闭环不是只发生在最终整体上。

每个小结构都必须把规则和质检内嵌为自身的一部分。如果某个小结构无法闭环，整个结构就无法闭环。

因此，它不依赖传统意义上的外部补丁来维持正确。问题不是被补丁遮住，而是被结构自身的闭环条件识别出来，并回到结构内部继续修正。

## 公开原则

这个项目的公开版本应当满足三个条件：

1. 读者能理解它为什么不是传统程序设计方法的简单变体。
2. 读者能看到一个最小例子，理解输入如何转化为状态演化与输出。
3. 读者能运行一个最小实现，而不是只阅读抽象概念。
